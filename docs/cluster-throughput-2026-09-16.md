# 集群审核吞吐与取消检查（2026-09-16）

## 定位结果

251 的原 InsightFace 未设置 CPU 硬配额，两个集群副本此前各限制为 4 CPU。
同一视频 98 秒处、含 10 张人脸的单帧只读检测和检索，原主节点约 2.53 秒，
副本 A 约 14.27 秒，副本 B 约 16.09 秒。副本 A 临时调整到 8 CPU 时约 8.25 秒，
16 CPU 时约 3.88 秒；探测后先恢复了原配置。模型配置相同，副本有大量 CPU 节流时间。
这些为同机单次样本，不能视为通用容量或推荐配额。

审核日志中的活动窗口多数已达到 6 个。用户取消的任务里，第 31 个窗口至少持续了 146 秒。
进度条按连续完成的视频前缀推进，该窗口未完成时，后续完成的窗口不会越过它推进时间轴。
同步人脸 SDK 一次操作包含检测和逐脸查询，原先取消只等待整个 SDK 线程结束，后续子请求仍会发送。

## 修复与边界

- 默认 Compose 不声明 CPU 配额，显式加载 compose.cpu-limits.yaml 才会限制；任务和窗口仍必须限流。
- 人脸每轮操作向全部子请求传递剩余时限，取消后禁止下一次请求。
- OCR、visual、guard 的异步 HTTP 请求关闭响应流再释放名额，视觉回退沿用同一轮剩余时限。
- 独立文字/视觉审核与人脸视频搜索统一异步下载，取消会关闭连接并清理临时视频。
- S3 发送钩子在每次请求及内部重试前检查取消；结果归档线程排空当前请求后退出。
- 反复取消不会提前释放同步调用的锁或租约；取得资源时发生取消则回收新取得的资源。
- 模型超时与人工取消重叠时仍等待内部清理，人工取消不触发新的模型重试。
- 人物写入补偿、不确定写隔离及原主节点数据格式保持原规则。

当前上游已接收的推理不保证立即停止；同步线程仍需等待当前网络调用结束，不能强行丢弃锁和读取租约。
